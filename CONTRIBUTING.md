# Contributing

Thanks for taking the time to contribute! This repository is a collection of
reusable, security-focused Terraform modules for AWS. The guidelines below keep
the modules consistent and the review process smooth.

## Ways to contribute

- **Report a bug** — open a [bug report](https://github.com/pierrehanne/terraform-services/issues/new?template=bug_report.yml).
- **Request a feature or new module** — open a [feature request](https://github.com/pierrehanne/terraform-services/issues/new?template=feature_request.yml).
- **Improve documentation** — module `README.md` files, the docs site, or examples.
- **Submit code** — bug fixes, new modules, or enhancements via a pull request.

If you're planning a larger change (a new module, or reworking an existing one),
please open an issue first so we can align on the approach before you invest time.

## Development setup

You'll need:

- [Terraform](https://developer.hashicorp.com/terraform/downloads) (see each
  module's `versions.tf` for the required version)
- [pre-commit](https://pre-commit.com/)
- [terraform-docs](https://terraform-docs.io/)
- [tflint](https://github.com/terraform-linters/tflint)

Install the pre-commit hooks once after cloning:

```bash
pre-commit install
```

The hooks run `terraform fmt`, `terraform validate`, `terraform-docs`, and
`tflint` on every commit — the same checks that run in CI.

## Making a change

1. **Fork** the repository (or create a branch if you have write access).
2. Create a topic branch from `main`. Use a descriptive, prefixed name that
   matches the project convention, e.g. `feat/vpc-peering` or `fix/kms-alias`.
3. Make your change, keeping it focused — one logical change per PR.
4. Run the checks locally (see below).
5. Push and open a pull request against `main`.

## Coding standards

- **Formatting** — all `.tf` files must pass `terraform fmt`. The pre-commit
  hook enforces this.
- **Validation** — `terraform validate` must pass for every module you touch.
- **Documentation** — module input/output tables are generated by
  `terraform-docs`. Keep the `BEGIN_TF_DOCS` / `END_TF_DOCS` markers in each
  module `README.md` intact; the docs are regenerated automatically in CI.
- **Security by default** — modules should be safe out of the box: encryption
  enabled, least-privilege IAM (no `*` on `Allow`), no public exposure unless a
  variable explicitly opts in.
- **Examples** — new modules should ship a runnable example under
  `aws/<module>/examples/`.
- **Variables & outputs** — every variable needs a `description` and a `type`;
  use sensible, secure defaults; mark secrets `sensitive = true`.

Run everything at once before pushing:

```bash
pre-commit run --all-files
```

## Commit messages

This project follows [Conventional Commits](https://www.conventionalcommits.org/).
Use a type prefix and an optional scope:

```
<type>(<scope>): <short summary>
```

Common types used here: `feat`, `fix`, `docs`, `ci`, `chore`, `refactor`.
Examples from the history:

- `feat(network): add NAT strategy enum`
- `fix(secret): refactor outputs`
- `docs: add bedrock guardrail module`
- `ci: upgrade component versions`

## Opening a pull request

- Fill out the pull request template.
- Ensure CI is green (see [Continuous integration](#continuous-integration)).
- Link any related issue (`Closes #123`).
- Keep the PR scoped to a single concern; split unrelated changes.
- Be responsive to review feedback — maintainers review on a best-effort basis.

## Continuous integration

Every pull request runs the **CI** workflow (`.github/workflows/ci.yml`), which
gates the merge on:

- **`fmt`** — `terraform fmt -check -recursive` across the repo.
- **`validate`** — `terraform validate` for each module in `aws/*`, run as a
  matrix (a job per module, discovered automatically).
- **`tflint`** — the AWS ruleset per module, using the shared `.tflint.hcl`.

A **`security`** job (Trivy IaC scan) also runs, but it is **report-only**:
findings are uploaded to the repository's **Security → Code scanning** tab and
never block a merge. Triage them there.

These are the same checks the pre-commit hooks run locally, so
`pre-commit run --all-files` should pass before you push.

All jobs feed a single **`CI success`** gate job, which fails unless `fmt`,
`validate`, and every `tflint` matrix job succeeded.

> **Maintainers:** enforce CI with a branch protection rule on `main`. Under
> **Settings → Branches → Branch protection rules**, require the **`CI success`**
> status check to pass before merging. That one check is enough — it aggregates
> `fmt`, `validate`, and `tflint`, so it stays correct even as modules are added
> or removed from the matrix.

## Releases

Releases are tagged manually via the **Tag Release** GitHub Actions workflow.
Versions follow [Semantic Versioning](https://semver.org/) (`vX.Y.Z`) and must
strictly increment. Only maintainers can cut releases.
